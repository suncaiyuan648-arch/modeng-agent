# CCR-0002: ModelExecutionPort@1 for the Fake TALK vertical slice

## Metadata

- Contract owner: `backend-model-supply`
- Requested by: WP-004 Fake TALK End-to-End Vertical Slice
- Current version: no business Model Execution Port; Model Supply is
  bootstrap-only
- Proposed version: `ModelExecutionPort@1`
- Compatibility: additive versioned public surface; there are no existing
  business consumers to preserve
- Status: APPROVED / PLANNING RECORD
- Architecture review: `ADR required = NO`

## Authorization

- `packages/backend/model-supply/src/index.ts`
- `packages/backend/model-supply/module.manifest.json`

## Decision

WP-004 needs one stable seam between the TALK capability and Model Supply so a
Fake Model can prove the vertical slice without importing a Provider SDK or
making the capability own model-execution infrastructure. This CCR approves
only `ModelExecutionPort@1`, owned by Model Supply.

The implementation may update the following controlled public metadata and
contract surface after this CCR is merged and all other WP-004 implementation
entry gates are closed:

- `packages/backend/model-supply/src/index.ts` for the package-root public Port
  contract;
- `packages/backend/model-supply/module.manifest.json` to declare the Port and
  its conformance ownership;
- the WP-004 Plan's already-authorized Model Supply implementation and test
  paths for Fake/real adapter conformance.

This CCR authorizes no implementation in its planning diff and does not change
the current implementation branch permission by itself.

## Problem

The TALK capability must request bounded model execution through the Model
Supply owner. The current Model Supply package exports only its bootstrap
identity, so implementing the first Fake TALK slice would otherwise require a
private cross-module callback with no stable owner/version or a forbidden
Provider SDK dependency in a capability.

## Proposed contract

The following is the complete v1 semantic surface. The final TypeScript and
runtime validation details must remain at the Model Supply package root and
must reject unknown required fields.

```ts
type ModelExecutionPlanRefV1 = {
  schemaVersion: 1;
  planId: string; // opaque Model Supply plan identity
};

type ModelExecutionRequestV1 = {
  schemaVersion: 1;
  plan: ModelExecutionPlanRefV1;
  input: {
    text: string; // bounded business input; no control marker semantics
  };
  context: {
    operationId: string;
    projectId: string;
    capability: 'talk';
  };
};

type ModelExecutionDeltaV1 = {
  schemaVersion: 1;
  ordinal: number;
  text: string;
};

type ModelExecutionHandleV1 = {
  stream: AsyncIterable<ModelExecutionDeltaV1>;
  abort: (reason?: 'lifecycle' | 'timeout') => Promise<void>;
};

interface ModelExecutionPortV1 {
  execute(
    request: ModelExecutionRequestV1,
    options?: { signal?: AbortSignal },
  ): Promise<ModelExecutionHandleV1>;
}
```

The exact exported declarations may use repository-native branded identifiers
and schemas, but they must preserve these invariants:

- `planId` is opaque to consumers. The Port owns plan interpretation; the
  request has no provider, model, credential, routing, or raw provider-data
  fields.
- `input.text` remains ordinary TALK business text. Failure behavior is
  injected through Fake adapter/test composition configuration and never by a
  user-text marker or command field.
- `context` is an allowlisted execution reference only. It must not carry a
  system prompt, hidden reasoning, raw event, persistence record, credential,
  or unbounded arbitrary object.
- `stream` yields normalized text deltas with deterministic ordinal ordering;
  it does not expose Provider response shapes.
- `abort` and `AbortSignal` are internal lifecycle/timeout cleanup primitives.
  WP-004 does not expose them through `TalkSubmitCommand`, HTTP/SSE, UI, or a
  Stop control, and does not authorize a user-visible generation cancellation.
  A future Cancel Contract must define that behavior separately.
- Errors map to existing sanitized `PlatformError` codes, at minimum
  `INVALID_INPUT`, `DEPENDENCY_UNAVAILABLE`, `TIMEOUT`, `CANCELLED` for an
  internal lifecycle abort, and `INTERNAL_ERROR`. Consumers branch on stable
  codes, never on error messages or Provider details.

## Explicit non-scope: no Port surface expansion

This CCR does **not** approve or freeze any of the following as public/versioned
Ports in WP-004:

- `TaskEnginePort`;
- `CapabilityOutputPort`;
- `EventStreamPort`;
- `AgentRuntimePort`.

For this first Vertical Slice each of those interactions has one in-process
composition consumer and can remain a package-root factory/private callback
inside its existing Owner boundary. If implementation proves that one of them
must become a public/versioned Port, stop and submit a separate focused CCR;
do not extend CCR-0002 for future convenience.

## Compatibility and affected modules

- Owner: `backend-model-supply` owns plan identity, adapter execution, error
  normalization, and Fake/real conformance.
- Consumer: `backend-capability-talk` calls the Port through the approved
  package root. `backend-agent-runtime` and Event & Realtime retain their
  existing lifecycle/event ownership and do not become Model Port consumers.
- Composition: the API-local/in-memory Fake composition may inject a Fake
  adapter and its failure mode. No production Provider, Worker, queue, Redis,
  persistence, or credential behavior is introduced.
- Package boundary: the public root gains only `ModelExecutionPort@1`; no deep
  import, transitive internal re-export, new module, Owner, or dependency
  direction is authorized.
- Versioning: changing required fields, stream semantics, abort semantics,
  error meaning, or plan identity requires `ModelExecutionPort@2` or a new
  focused CCR. Adding a new Provider or adapter does not permit changing v1.

## Fixtures and conformance

The later implementation must provide one shared Model Execution conformance
suite and run it against the configured Fake adapter and any real adapter that
is introduced under a separately approved scope. The suite must cover:

1. bounded valid input and rejection of oversized/unknown input fields;
2. opaque plan identity and allowlisted context only;
3. normalized deltas, ordinal ordering, bounded output, and stream completion;
4. duplicate invocation behavior and deterministic idempotency expectations;
5. Fake failure injected by composition configuration, with ordinary user text
   remaining unchanged;
6. lifecycle/timeout abort behavior without exposing a generation-stop control
   or changing the Operation cancellation Contract;
7. stable PlatformError mapping, retryability, and no raw Provider/internal
   data, credentials, prompts, or hidden reasoning;
8. Fake and real adapter parity for every v1 behavior.

The CCR planning diff adds no schema, fixture, test, adapter, manifest, or
runtime implementation. Those changes belong to the WP-004 implementation
branch after this CCR is merged.

## Architecture and ADR decision

`ADR required = NO` for the described implementation because it preserves the
modular-monolith process, existing Model Supply Owner, existing dependency
direction, in-process composition, and existing cancellation boundary. The
Port's internal lifecycle abort is not a user Cancel Contract and does not add a
new Operation status.

Stop and request an ADR before coding if review or implementation proposes any
of the following: a new process or queue, production Worker handoff, a new
Owner/table/consistency boundary, a dependency-direction change, persistent
model-execution facts, a Provider contract beyond this Port, or user-visible
Operation cancellation.

## Forbidden changes

This CCR must not be used to:

- add provider/model/credential fields to `TalkSubmitCommand`;
- add a user-text failure marker or change Talk text semantics;
- add a network event, Operation status, billing field, migration, feature flag,
  retention policy, queue, Worker, Redis, Prisma, or Provider SDK;
- add `StopButton`, `stop-viewing`, or any UI that implies backend cancellation;
- freeze `TaskEnginePort`, `CapabilityOutputPort`, `EventStreamPort`, or
  `AgentRuntimePort`;
- expose raw Provider data, system prompts, hidden reasoning, credentials,
  stack traces, or internal persistence details.
