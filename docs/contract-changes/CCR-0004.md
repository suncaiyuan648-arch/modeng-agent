## Problem

The current Agent Runtime owns Operations, Graphs, accepted Events, and command
idempotency in Maps, while Event & Realtime exposes a synchronous
`InMemoryEventStream`. PostgreSQL adapters cannot replace those stores without a
stable Owner-defined Port, and the accepted/terminal projection plus Event pairs
cannot be made atomic without a narrow transaction composition seam.

Freezing every first-pass CRUD function would create a shallow permanent public
API. Conversely, exposing Prisma or an arbitrary Unit of Work callback would let
consumers bypass state Owners. WP-006 therefore needs three small behavioral Ports
with transaction-scoped mutation participants hidden behind one TALK-specific
composition boundary.

## Proposed change

The final exported TypeScript may use repository-native branded IDs, readonly
types, and runtime schemas. It must preserve the complete v1 semantics below and
must not add arbitrary query objects, raw records, ORM types, or unvalidated
serialized data.

### 1. AgentRuntimePersistencePort@1

Agent Runtime owns this async Port and the persisted Operation, Graph, Node, and
Command Receipt invariants.

```ts
type TalkFingerprintDigestV1 = {
  algorithm: 'sha256-v1';
  digest: string; // fixed-length lowercase SHA-256 hex
};

type VersionedOperationSnapshotV1 = {
  operation: OperationRef;
  version: number; // bounded optimistic version; not a storage record
};

type NonTerminalOperationPageV1 = {
  items: readonly VersionedOperationSnapshotV1[];
  nextCursor?: string; // opaque stable keyset cursor
};

interface AgentRuntimePersistencePortV1 {
  getOperation(operationId: OperationId): Promise<OperationRef | undefined>;

  listNonTerminalOperations(input: {
    after?: string;
    limit: number;
  }): Promise<NonTerminalOperationPageV1>;
}
```

The public read Port deliberately exposes no `findMany`, SQL predicate, generic
CRUD, Prisma record, receipt lookup, or cross-Owner join. `limit` is bounded.
Pagination order and cursor encoding are adapter-independent opaque behavior; a
caller repeatedly follows `nextCursor` until absent.

The transaction-scoped `AgentRuntimeMutationPortV1` is exported only as the
participant type required by `TalkRuntimeUnitOfWorkPort@1`; it is not a separately
registered injectable Contract. It supports only:

- claiming a principal-scoped TALK command by idempotency key and versioned
  fingerprint digest while atomically creating its Operation, Graph, one TALK
  node, and receipt;
- returning the previously committed Operation reference for an identical claim;
- throwing existing safe `CONFLICT` for the same scope/key with a different
  digest; and
- conditionally transitioning an Operation using expected version and the
  existing state-transition rules, without overwriting a terminal state.

The claim input carries the already validated command facts and server-supplied
principal scope. It never stores the canonical fingerprint string, treats a
client field as identity, or accepts an arbitrary persistence record. The
mutation result distinguishes `created` from `duplicate` and supplies only the
Owner facts needed to build or return the existing accepted Event. A created or
duplicate claim returns a `VersionedOperationSnapshotV1`; a successful conditional
transition returns the snapshot with its incremented version; and a rejected
transition reports `version-conflict` or `already-terminal` without supplying a
writable record. Startup reconciliation therefore uses the version returned in
each keyset-page item as `expectedVersion` and never guesses or re-reads an
unversioned projection.

### 2. EventStorePort@1

Event & Realtime owns Event envelope validation, Event ID idempotency,
per-Operation sequence allocation, replay, terminal detection, and local live
subscription.

```ts
type WithoutSequence<T> = T extends unknown ? Omit<T, 'sequence'> : never;
type EventAppendIntentV1 = WithoutSequence<KnownEventEnvelope>;

interface EventStorePortV1 {
  replay(operationId: OperationId, afterSequence?: number): Promise<readonly EventEnvelope[]>;

  subscribe(
    operationId: OperationId,
    afterSequence?: number,
    options?: { signal?: AbortSignal },
  ): AsyncIterable<EventEnvelope>;
}
```

The transaction-scoped `EventMutationPortV1` is exported only as the Event
participant type consumed inside `TalkRuntimeUnitOfWorkPort@1`; it is not a
separate injectable Contract. It has one operation:

```ts
interface EventMutationPortV1 {
  append(intent: EventAppendIntentV1): Promise<EventEnvelope>;
}
```

Agent Runtime defines the existing business Event type/payload and supplies a
validated intent; Event & Realtime alone validates the full envelope, allocates
and returns `sequence`, and enforces append idempotency. Runtime code must not
preallocate a sequence. Repeating an identical `eventId` returns the existing
committed Event; the same ID with different canonical content throws existing
safe `CONFLICT` and never edits history. The equality check covers the immutable
append intent (`schemaVersion`, `eventId`, `operationId`, `occurredAt`, `type`, and
typed `payload`); it does not compare a retry input with a caller-supplied sequence,
because callers never supply one.

Before a new Event commits, Event & Realtime validates the sequence-assigned
candidate against the committed Operation stream. A delta before acceptance, a
second accepted Event, an Event after a committed terminal Event, or any other
existing stream-invariant violation is rejected rather than appended.

`UnknownNonCriticalEvent` remains a forward-compatible **decoder** branch for
replay/network consumption and can still appear in the `EventEnvelope` return
type. It is never a producer intent. `append()` runtime validation rejects an
unknown/non-approved Event type even if it would be safe for an older consumer to
ignore; adding producer semantics requires its own shared Contract/CCR.

`replay` validates a non-negative integer cursor and returns only committed Events
whose sequence is greater than it, ordered strictly ascending. Values loaded from
database JSON remain `unknown` until the existing Event envelope parser succeeds.
The Port does not expose `delivery_position`, SQL pagination, uncommitted Events,
or storage records.

`subscribe` implements replay-to-live as a database-authoritative stream:

1. replay after the cursor and complete if a terminal Event is reached;
2. register a buffered/generation-aware local wake-up;
3. catch up from the database after registration, deduplicating by monotonically
   advancing sequence;
4. before every wait, including after an empty catch-up/query, perform an
   Owner-local committed-tail check and complete if terminal is at or before the
   cursor; and
5. after each signal, query committed Events again rather than trusting a signal
   payload.

If `afterSequence` equals or exceeds the committed terminal sequence, subscription
emits no duplicate history and completes immediately without leaking a waiter.
Signals are post-commit hints only. This v1 Contract provides no cross-node fan-out
guarantee; reconnect/replay is the recovery path.

Aborting `options.signal` ends the iterator promptly and unregisters every local
waiter without emitting a business Event or changing durable facts. API SSE
teardown must abort the iterator (or equivalently call and await its `return()`);
setting a local `closed` flag while leaving a pending waiter is not conformant.

### 3. TalkRuntimeUnitOfWorkPort@1

Agent Runtime owns this application-layer, TALK-specific composition Port:

```ts
type TalkRuntimeMutationScopeV1 = {
  agentRuntime: AgentRuntimeMutationPortV1;
  events: EventMutationPortV1;
};

type AcceptedEventV1 = Extract<KnownEventEnvelope, { type: 'operation.accepted' }>;
type DeltaEventV1 = Extract<KnownEventEnvelope, { type: 'talk.output.delta' }>;
type TerminalEventV1 = Extract<
  KnownEventEnvelope,
  { type: 'operation.completed' | 'operation.failed' }
>;

type TalkRuntimeUnitOfWorkResultV1 =
  | {
      kind: 'submission-created';
      operation: VersionedOperationSnapshotV1;
      acceptedEvent: AcceptedEventV1;
    }
  | { kind: 'submission-duplicate'; operation: VersionedOperationSnapshotV1 }
  | {
      kind: 'nonterminal-transition-applied';
      operation: VersionedOperationSnapshotV1;
    }
  | { kind: 'delta-appended'; events: readonly [DeltaEventV1, ...DeltaEventV1[]] }
  | {
      kind: 'terminal-applied';
      operation: VersionedOperationSnapshotV1;
      event: TerminalEventV1;
    }
  | { kind: 'transition-not-applied'; reason: 'version-conflict' | 'already-terminal' };

interface TalkRuntimeUnitOfWorkPortV1 {
  run(
    work: (scope: TalkRuntimeMutationScopeV1) => Promise<TalkRuntimeUnitOfWorkResultV1>,
  ): Promise<TalkRuntimeUnitOfWorkResultV1>;
}
```

The infrastructure implementation builds both mutation participants over one
short PostgreSQL transaction. The scope is opaque to the callback: it exposes no
Prisma client, transaction handle, raw query, commit/rollback function, arbitrary
Owner lookup, or generic repository. `run()` resolves only after commit and
rejects on rollback. Its returned discriminated union is parsed by an Agent
Runtime-owned runtime schema before commit; a scoped participant, transaction
value, arbitrary object, or mismatched result therefore cannot escape as the
result.

The UoW wrapper maintains an internal mutation ledger and checks it before commit.
Only these shapes are valid:

- `submission-created`: exactly one newly claimed Operation/Graph/Node/receipt and
  exactly one matching `operation.accepted` Event whose payload references those
  same facts;
- `submission-duplicate`: one identical existing receipt claim and no new Owner
  mutation or Event;
- `nonterminal-transition-applied`: exactly one conditional
  `accepted -> running` Operation projection mutation, its incremented version,
  and no Event (the frozen Contract has no `operation.running` Event);
- `delta-appended`: a bounded non-empty group of idempotent/new
  `talk.output.delta` Events for one accepted, non-terminal Operation and no Agent
  Runtime projection mutation;
- `terminal-applied`: exactly one successful conditional transition and exactly
  one matching `operation.completed` or `operation.failed` Event whose payload
  contains the resulting projection and status; or
- `transition-not-applied`: a version/terminal no-op and no new Event.

A claim without its accepted Event, an accepted Event without its claim, either
side of a terminal pair, a mismatched Operation/status/payload, mixed Operations,
an unknown Event, an empty delta group, a nonterminal transition other than
`accepted -> running`, a running transition accompanied by any Event, or any extra
mutation fails pre-commit validation and rolls back the whole transaction.

Every scoped method performs an active-scope check and is tracked by the wrapper.
After the callback returns, the wrapper closes the scope to new calls, awaits all
already-started scoped calls, validates the result/ledger, and permanently
invalidates both participants before resolving. Calling a captured participant
afterward fails safely and cannot reach storage.

The implementation may use bounded whole-transaction retries for recognized
serialization/allocator conflicts. The callback may therefore be re-entered and
must perform no external side effect. Provider/HTTP/OSS I/O, Task execution, SSE
waiting, timers, and stream consumption are forbidden inside it.

Identifiers, timestamps, digest inputs, and Event intents used by a retried
mutation are created before `run()` or otherwise remain identical across callback
re-entry. A callback must not call a clock/random-ID source on each attempt and
thereby turn one logical mutation into different facts.

Event & Realtime's composition may collect post-commit wake-up intents while the
callback runs, but it publishes them only after the transaction promise succeeds.
Rollback publishes none. This Port is used only for the complete closed
mutation-ledger shapes enumerated above and approved by ADR-0003; it is not a
platform-wide Unit of Work framework.

A wake-up dispatch failure after commit cannot reject or reclassify the committed
unit of work as rolled back. It is sanitized/observed as a non-authoritative
delivery failure; clients recover the committed Event through replay.

### 4. Existing facade compatibility

The non-versioned `AgentRuntime` facade becomes asynchronous where it reads or
commits durable state:

```ts
interface AgentRuntime {
  submit(input: unknown): Promise<AgentRuntimeSubmitResult>;
  getOperation(operationId: OperationId): Promise<OperationRef | undefined>;
  getAcceptedEvent(operationId: OperationId): Promise<EventEnvelope | undefined>;
  hasOperation(operationId: OperationId): Promise<boolean>;
}
```

`getAcceptedEvent` may obtain the accepted Event through `EventStorePort@1`; it
does not make Agent Runtime an Event-store Owner. `AgentRuntimeSubmitResult`, HTTP
accepted response, Event envelope, SSE framing, and status/error schemas remain
unchanged. Existing API consumers must await the in-process facade, but browser
network compatibility is preserved.

The existing in-memory Event implementation becomes the Fake for
`EventStorePort@1` and the transaction participant used by the Fake UoW. The
implementation may retain familiar factory naming for coordinated repository
tests, but its async/sequence-allocation semantics must conform to v1. No second
production in-memory authority may remain behind the facade.

### 5. PostgreSQL composition-only surface

`packages/infrastructure/persistence-postgres/src/index.ts` may export one
non-versioned composition-only factory that accepts backend database configuration
and returns implementations of:

- `AgentRuntimePersistencePort@1`;
- `EventStorePort@1`;
- `TalkRuntimeUnitOfWorkPort@1`; and
- a bounded lifecycle close function needed by API shutdown.

Startup reconciliation remains Agent Runtime behavior over the approved Ports;
the infrastructure factory must not become a business service or own readiness
policy. The package root must not expose PrismaClient, generated models, adapter
internals, raw transaction callbacks, table DTOs, `DATABASE_URL` contents, or a
general resolver/registry.

## Fixtures and conformance

The implementation must prove at least:

1. new receipt claim creates one Operation/Graph/Node/receipt, while concurrent
   same-scope/key/same-digest requests return the same accepted Event and
   Operation;
2. same scope/key with a different digest returns existing safe `CONFLICT`, while
   different scopes or keys remain independent;
3. receipt persists only the algorithm version and fixed-length digest, never the
   canonical prompt/fingerprint;
4. Operation transition uses expected version, accepts only the existing state
   machine, returns the next version when applied, and cannot overwrite terminal
   state; reconciliation consumes the versioned page snapshot; the sole
   projection-only success is `accepted -> running`, with no Event, while every
   wrong nonterminal transition, attached Event, extra mutation, or injected
   storage failure rolls back;
5. non-terminal keyset pagination reaches exhaustion across more than one page and
   repeated reconciliation creates at most one terminal Event;
6. concurrent Event append, multiple appends in one transaction, transaction
   rollback/retry, Event ID identical retry, Event ID content conflict, and strict
   per-Operation sequence behavior, including rejection before acceptance and
   after terminal; producer append rejects `UnknownNonCriticalEvent` and any
   non-approved type;
7. replay ordering and cursor validation, replay/register/catch-up races, duplicate
   signals/results, no uncommitted delivery, committed terminal completion, and
   `afterSequence == terminalSequence` plus `afterSequence > latestSequence`, as
   well as consumer abort/iterator return releasing a pending waiter;
8. accepted and both terminal projection/Event pairs commit or roll back together;
   rollback produces no live signal and a successful commit signals only after
   commit, while a post-commit signal failure preserves the committed result;
   every incomplete, extra, mixed-Operation, or payload/status-mismatched mutation
   ledger rolls back;
9. whole-UoW retry does not duplicate external side effects or produce a second
   Operation/Event; a captured scoped participant and an invalid callback result
   are rejected after callback completion;
10. production runtime has no in-memory idempotency guard/Map authority, and API
    restart returns the same Operation/Event history from PostgreSQL; and
11. errors are existing sanitized `PlatformError` codes with no SQL, connection
    string, stack, prompt, raw Provider data, or hidden reasoning.

Agent Runtime implementation tests separately cover deterministic delta
coalescing, flush-before-terminal, no transaction per Provider frame, immediate
TaskRun create/start failure convergence, and fail-closed startup. These are
required WP-006 behaviors but not additional public Port fields.

## Compatibility and affected modules

- Public shared/network Contract: no change to
  `packages/shared/contracts/src/**`, `TalkSubmitCommand@1`, Event/SSE schemas,
  Operation statuses, Platform Error codes, protocol major, or browser payload.
- Agent Runtime: its non-versioned facade becomes async and consumes its
  persistence/UoW Ports plus the Event Store Port; it remains Operation/Graph/
  Receipt Owner.
- Event & Realtime: replaces the synchronous in-memory stream surface with
  `EventStorePort@1` behavior and remains Event envelope/sequence/replay Owner; it
  does not define TALK business Event semantics.
- PostgreSQL adapter: implements, but does not own, the three Ports and exports
  only the composition factory.
- API: awaits the async facade and composes the PostgreSQL implementations. The
  controller does not import persistence internals or Prisma.
- Task Engine, Model Supply, TALK Capability, shared Contracts, frontend packages,
  and their public Contracts remain read-only.

This is a coordinated in-repository breaking change to non-versioned package-root
facades. There is no v1/v2 network coexistence window because WP-006 uses the
non-overlapping single-process rollout required by ADR-0003.

## Forbidden changes

This CCR must not be used to:

- add or modify a shared runtime Contract, Event/SSE field, status, error code,
  protocol major, cancellation behavior, or browser request field;
- add an arbitrary query/filter/CRUD surface, generic Repository/DAO, global Unit
  of Work, Prisma type/client, raw SQL, transaction handle, or Owner registry;
- let Agent Runtime allocate Event sequence/write `ai_event`, let Event & Realtime
  write Agent Runtime tables, or assign business table ownership to infrastructure;
- export `AgentRuntimeMutationPortV1` or `EventMutationPortV1` as independently
  injectable Manifest Contracts beyond the scoped type roles specified here;
- add TaskRun persistence, Outbox, Worker, BullMQ, Redis, Lease, checkpoint,
  Conversation, ProviderExecution, Billing, Artifact, Model Catalog, or another
  Capability;
- add rolling/multi-instance live semantics, LISTEN/NOTIFY, Redis Pub/Sub, or
  automatic Provider continuation;
- modify architecture sources, trusted workflow/configuration files, existing
  accepted ADR/CCR, or introduce a real database credential; or
- widen the PostgreSQL composition factory into a business resolver or expose
  connection configuration through logs, errors, or browser code.

If implementation needs a forbidden surface or a semantic change to one of the
three v1 Ports, stop and submit a focused CCR and, where the consistency/Owner/
dependency boundary changes, a focused ADR.

## Architecture decision

`ADR required = YES`. ADR-0003 must be accepted and merged with this CCR before
implementation because WP-006 introduces the first business Migration/table
ownership, persistence dependency edges, per-Operation advisory-lock sequence
allocator, cross-Owner atomic transaction, and non-overlapping deployment rule.

This CCR does not itself authorize those RED architecture paths. ADR-0003 does not
replace the Contract authorization in this record; the two approvals are jointly
required in the implementation branch BASE SHA.

## Migration / rollout / rollback

1. Review and merge this governance-only CCR with ADR-0003 to `main`.
2. Create the implementation branch from a `main` that contains the WP-006
   Planning Record, accepted ADR-0003, and approved CCR-0004.
3. Implement the Fake conformance harnesses and PostgreSQL adapters without
   expanding the authorized package-root surface.
4. Switch the API composition only after clean Migration, restart, concurrency,
   replay/live-race, reconciliation, and full existing verification pass.

Before implementation, rollback is a documentation-only revert of this CCR and
ADR-0003. After implementation, v1 behavior cannot be silently changed: roll
forward with a compatible fix or propose a new focused/versioned Contract. This
record adds no runtime, database, credential, queue, configuration, or external
side effect by itself.
